# Agent-run acceptance for the everyday macOS experience

Research for [Establish agent-run acceptance for the macOS desktop experience](https://github.com/apshenichniy/trigo/issues/69), checked on 2026-09-08. Code references below pin the inspected main commit `8e65ee1b6f11421d3102b6ec75911720d5b8bf96`. This report proposes a delivery path; it does not claim that a UI harness or new installed acceptance has run.

## Recommendation

Make executable UI acceptance an early implementation slice of [Design the everyday Trigo desktop experience](https://github.com/apshenichniy/trigo/issues/8). Agents can own implementation, deterministic tests, UI interaction and visual review, signed installation, evidence collection and integration once implementation is authorized. A prepared GUI runner and the required signing/access grants are external preconditions for the installed portion. No current evidence supports a promise that agents can obtain every first-time macOS consent without owner involvement.

Use three distinct evidence layers: deterministic native tests, the actual app UI with isolated fixtures, and controlled capture through the installed signed app. Keep physical keyboard/device observations and the owner's final Meet/Telegram calls separately labelled. Neither a fixture transcript nor an animated meter proves hosted transcription or physical microphone capture.

The agreed flow is global **Start**, then Trigo microphone recording mute and **Finish** in the floating panel; finishing hides the panel. Pause/resume is excluded. The library has a date-grouped sidebar, transcript reader and fullscreen support, with Dock/Command-Tab presence while the library is open. Detailed repeated-gesture and transitional/error presentation remain with the design decisions; this research does not select those policies.

## Minimal implementation slices

### 1. Launchable fixture composition and one GUI smoke test

Add an XCTest UI test target and scheme in `project.yml`, plus a test-only application composition using the same scene, delegate and views as the shipped app. Apple distinguishes Swift Testing for direct unit/integration tests from XCTest's UI-test support. XCTest launches an app with explicit arguments/environment, so agents can select scenarios without clicking a debug setup screen. [Adding test targets][apple-test-targets], [launch arguments][apple-launch-args], [launch environment][apple-launch-env]

The fixture contract should carry an allowlisted scenario name, unique temporary storage root, reproducible clock/calendar inputs and optional retained fixture namespace for a relaunch test. Inject source access, permission results, capture transport and test credentials at composition boundaries; use the real coordinator and repository underneath. Keep this code in test-only build inputs and make fixture launches fail closed if they select Personal data or production credentials.

A dedicated fixture app identity also needs explicit variant handling: the current app treats only the exact Dev bundle ID as Dev, and otherwise selects Personal. Simply inventing a new bundle identifier would therefore be unsafe without changing this composition boundary. Installed namespace construction currently accepts only `--local-config` and otherwise uses Application Support. [App initialization][code-app], [namespace construction][code-namespace]

The first passing smoke test must launch with no library window, find the menu-bar item, open the library, close it and confirm that the process remains available in the menu bar. This resolves the previously observed automation uncertainty early. No global gesture, microphone, ScreenCaptureKit consent or hosted server is needed for this fixture smoke.

### 2. Behavioral UI suite and review artifacts

Use stable accessibility identifiers, values and state-based waits, with screenshots for visual review. Apple's UI automation recognizes SwiftUI accessibility identifiers, while screenshots can be attached to test results. An obscured macOS window can produce a screenshot containing the covering window, so use one serialized GUI runner and a controlled desktop when collecting visual evidence. [Identifier guidance][apple-ui-guidance], [screenshots][apple-screenshot], [occlusion behavior][apple-screenshot-occlusion]

Minimum fixture coverage:

Policy alone is not the entire shell/UI proof. |
| Active recording               | Start uses the scripted frontmost source before presentation; the panel appears for the accepted recording state; focus changes preserve source identity. Mute changes only the microphone contribution; Finish finalizes the same call and hides the panel.                                                    | Deliver synthetic shortcut intent through the production action boundary. This does not prove a physical right-Control/Fn double tap.   |
| Measured levels                | Feed distinct known PCM envelopes through the transport/ingress seam. Assert independent numeric microphone/application levels and their UI values; acknowledged mute produces zero microphone contribution while application levels continue. Test silence, unavailable input and reduced-motion presentation. | Changing a displayed fixture number alone is insufficient. Compare level output with the post-mute samples admitted to recording.       |
| Archive and transcript         | Seed empty, multiple-day, ready, pending, failed, no-speech and interrupted calls. AppKit documents `.regular` as the ordinary Dock-visible policy and `.accessory` as Dock-hidden with programmatic/window activation available; `setActivationPolicy` reports whether a switch succeeded. SwiftUI's `MenuBarExtra` supplies a persistent system-menu-bar control, and Apple documents `LSUIElement` for menu-bar utilities absent from Dock and the app switcher. These APIs support the requested lifecycle, but its actual Dock, switcher and fullscreen behavior still needs GUI observation. [Regular policy][apple-regular], [accessory policy][apple-accessory], [policy switch][apple-policy], [menu-bar utility][apple-menu-bar]

A repository wrapper should run the selected Xcode scheme/test plan with `xcodebuild test`, keep an `.xcresult` plus fixture/run identity, and fail on missing tests, timeout or unavailable runner. It is a new command, not an existing capability. Apple supports running a whole plan or selected test with `xcodebuild`; the current repository commands only cover native suites, app builds and local Worker smoke. [Apple test execution][apple-test-execution], [current verification][code-verification]

### 3. Repeatable signed installed acceptance

Extend the existing install path and controlled fixture into an agent-run protocol; do not replace the installer. It already requires a signing team for normal install/run, verifies signatures, rejects unsupported bundle/worktree/designated-requirement replacements and refuses to replace a running destination. An isolated local configuration selects a worktree-specific install path and data namespace. [Signing/replacement policy][code-install-policy], [installer][code-installer], [namespace][code-namespace]

The installed protocol should verify the exact source/tree, app executable, bundle identifier, signing requirement, app path, local namespace and admitted source PID. On a prepared Mac, an agent can launch the signed app, open a dedicated controlled source, drive Start/mute/Finish, change focus, relaunch, and collect selected-call repository/master evidence. Never read unrelated calls or collect screenshots from private windows.

The existing Chrome fixture provides a known alternating 440 Hz application signal without network or microphone access. It asks a person to speak a marker and therefore does **not** by itself provide autonomous microphone stimulation. [Controlled fixture][code-audio-fixture] For repeatable non-private microphone input, provide a documented, pre-provisioned audio test arrangement with an independently identifiable microphone signal. If only acoustic playback into the built-in microphone is available, record the routing and report its acoustic-isolation limitation. If no controlled microphone stimulus is available, complete the application-audio installed check and keep the physical microphone observation explicit; an all-zero track cannot pass as positive microphone capture proof.

Promote the useful selected-call collector from the previous acceptance into a committed reusable tool: it must inspect only allowlisted call IDs, bound its reads, validate master/index and SQLite evidence, calculate channel/interval energy, and compare acknowledged mute intervals with exact zero microphone samples while preserving the application channel. The previous collector is referenced under `/tmp`, not a tracked reusable acceptance command. [Collector location][acceptance-status], [performed master/mute checks][acceptance-media]

Use the normal signed candidate for this layer. A fixture-only UI pass can prove the shared interface, but cannot establish the installed candidate's signing, real ScreenCaptureKit transport or Keychain behavior. Reuse matching build evidence according to the existing receipt rules; repeat affected checks when the candidate changes. [Build reuse][code-build-reuse]

## External preconditions and truthful limits

- **GUI automation:** Provision a usable macOS GUI session with the relevant test-runner control authorization. Apple documents Xcode Helper Accessibility approval for first UI recording and explicit authorization for accessibility control. This report did not test the current host's GUI runner, signing identity or grants. Prove them with the small smoke test; a tooling failure is an explicit blocker to the unattended UI gate, not permission to replace it with a manual screenshot checklist. [Xcode setup][apple-ui-recording], [Accessibility access][apple-accessibility]
- **Capture permissions:** Apple requires per-app microphone consent and documents user choices for screen/system-audio recording. Existing grants may suffice for the same supported signed identity, but the app cannot assume that a successful preflight eliminates every OS-owned reminder. The previous acceptance records a bounded successful rebuild observation, not a universal guarantee. [Microphone authorization][apple-microphone], [screen/audio consent][apple-screen-consent], [previous acceptance][acceptance-status]
- **Permission testing:** Routine UX acceptance uses injected permission states and requires no resets. XCTest exposes reset support for enumerated protected resources including microphone; the inspected public enum does not list Screen Recording or Input Monitoring. Its existence is not a universal TCC-control API. Expected consent dialogs should be queried explicitly; interruption monitors are for unexpected blocking UI, and Apple's documented implicit macOS handler may choose denial. Optional real consent tests belong in a dedicated disposable identity/session. [Protected resources][apple-protected], [reset API][apple-reset], [interruptions][apple-interruptions], [Apple explanation][apple-interruptions-talk]
- **Dev isolation is not TCC isolation:** Local Dev installations share the ordinary Dev bundle's macOS permission identity despite separate data/install paths. Do not reset ordinary Dev or Personal permissions for fixtures. No permission reset is required by this recommendation. [Installer's explicit identity boundary][code-shared-tcc]
- **Keyboard/hardware evidence:** Deterministic gesture-event sequences and synthetic GUI actions can establish recognizer and dispatch behavior. They do not establish physical right/left key or Fn hardware behavior, interaction with another installed app, Secure Event Input, or physical device removal. Retain these as narrowly described physical observations at final evaluation where applicable; do not require an exhaustive hardware matrix before agent delivery.

## Handoff and tracker consequence

[Validate failure recovery and the full first-slice acceptance](https://github.com/apshenichniy/trigo/issues/24) currently has a native blocker on [Demonstrate the complete real-call path in Meet and Telegram](https://github.com/apshenichniy/trigo/issues/23), as verified through GitHub's dependency API. The latter explicitly requires owner-operated calls and remains incomplete when fixtures alone pass. This is appropriate for final product signoff, but currently prevents the agent-run failure/recovery work from starting before those calls.

At [Define the UX and transcription handoff for autonomous delivery](https://github.com/apshenichniy/trigo/issues/70), partition machine-verifiable integrated acceptance and runnable-app delivery from that final real-call signoff. Agents should be able to build, check, review, integrate and deliver the complete candidate before the owner operates Meet/Telegram. Keep the real-call issue, final acceptance issue and [Complete the daily-call transcription and archive workflow](https://github.com/apshenichniy/trigo/issues/10) truthful about remaining real-use evidence; do not close them on fixture transcripts or controlled tones. Hosted ASR, cloud authorization and the provider/long-call requirements stay with their existing pipeline tickets.

The implementation handoff should name one GUI/installed-check executor, the required prepared environment, the fixture catalog and pass/fail artifacts, and the exact pending physical/real-call observations. It should not assign the maintainer intermediate screenshot collection, routine clicks or debugging tasks. Missing platform access remains an explicit environmental condition rather than an invented automated pass.
